# S3 — Fermeture complète : déroulé

> Décision D3 (PLAN §7) : release N compatible avec les anciennes **et** les nouvelles règles, puis hausse de `minimum_version` 2 à 4 semaines après, puis règles strictes et enforcement App Check.
>
> Objectif : fermer le dernier trou de S1, à savoir qu'un non-membre qui connaît un `groupId` peut encore s'ajouter lui-même. On en profite pour fiabiliser l'ordre des messages (K4) et activer App Check.

## Phase 1 — release N (code prêt, branche `s3/server-join`)

| Élément | État |
|---|---|
| Callable `joinGroupByCode` (`functions/src/invites/`) | ✅ Code écrit et testé (6 tests). Déployée |
| Ce que fait le callable | Vérifie le code d'invitation, puis ajoute le membre (`memberIds`, document membre `role: member`) et écrit le message système « 👋 X a rejoint le groupe », en un seul batch Admin |
| Cas « déjà membre » | Rien n'est écrit (G5) |
| Limitation de débit | 20 tentatives par heure et par compte (`rate_limits/join_{uid}`), contre l'énumération des codes |
| App Check sur le callable | `enforceAppCheck: false` pour l'instant, activé en phase 3 |
| Client : adhésion par code (feuille « Rejoindre » et lien d'invitation) | ✅ Passe par le callable. Le client n'écrit plus son document membre ni le message d'arrivée |
| K4 : horodatage serveur des messages | ✅ `FieldValue.serverTimestamp()` à chaque nouveau message. En attente d'accusé, `MessageMapper` retombe sur l'heure locale |
| Compatibilité | Les règles actuelles acceptent les deux clients : le callable passe par l'Admin SDK, et un horodatage serveur est un `timestamp`. Les versions ≤ 1.1.3 continuent de fonctionner sans changement |
| Bout en bout | Un second compte invité rejoint l'espace par code, via le callable sur l'émulateur Functions. Il voit les données et le message d'arrivée |

**Ce qu'il te reste à faire pour la phase 1 :**
1. Monter la version, par exemple `version: 1.2.0+203` dans `zyncro/pubspec.yaml` (actuellement `1.1.3+202`).
2. Publier la release Android et iOS.
3. Configurer **App Check** dans la console :
   - Android : Play Integrity, lié au compte Play Console ;
   - iOS : App Attest / DeviceCheck.

   Ne rien **enforcer** à ce stade : il faut d'abord suivre la proportion de requêtes vérifiées.

## Phase 2 — hausse de `minimum_version` (2 à 4 semaines après la release N)

Quand la part d'utilisateurs en version ≥ 1.2.0 est suffisante (statistiques Play Console / App Store Connect), modifier le document Firestore `config/app_version` :

```
minimum_version: "1.2.0"        (ou android_minimum_version / ios_minimum_version)
```

Les clients plus anciens affichent alors l'écran de mise à jour obligatoire. Cette logique existe déjà (`core/app_update`).

## Phase 3 — règles strictes et enforcement (après la phase 2)

À préparer sur une branche avec tests dans `firebase-tests/`, puis à déployer depuis la racine :

1. **Règles Firestore**
   - `groups/{gid}/members/{uid}` : création cliente uniquement **à la création du groupe**, quand le créateur crée son propre document `owner` dans le même batch que le groupe. Le chemin d'auto-ajout disparaît : seul le callable ajoute un membre.
   - `groups/{gid}` : plus d'`arrayUnion` de soi-même dans `memberIds` côté client (on garde le retrait de soi en quittant, et la gestion par le propriétaire).
   - `messages` : à la création, `request.resource.data.timestamp == request.time` (horodatage serveur obligatoire, ferme K4 pour de bon).
2. **App Check** : `enforceAppCheck: true` sur le callable (`ENFORCE_APP_CHECK`), puis enforcement dans la console pour Firestore, Storage et Functions, une fois la proportion de requêtes vérifiées proche de 100 %.
3. **Vérifications**
   - `firebase-tests` : flux de la release N autorisés, auto-ajout et horodatage client refusés ;
   - bout en bout ;
   - surveillance des `permission-denied` pendant 48 h ;
   - rollback = redéploiement des règles précédentes.

Optionnel, à décider plus tard (PLAN) : tokens d'invitation longs pour les liens et tokens FCM multi-appareils (G17).
